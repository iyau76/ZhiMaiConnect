## 2. 结构性缺陷（P0，重点）

> 根因定位：跨材料不可见、关系无法整理、重复边、一次字段错误整单报废等问题，最终都指向同一个结构性问题——**Agent Loop 是"补丁式"生长出来的，不是按领域对象设计的**。详见 S1。

### S1. 结构性根因：Agent Loop 是"补丁式"生长，关系从未成为 loop 里的一等对象

**历史成因**：录入最初是单次 LLM 调用——材料进、整包草稿 JSON 出，没有 loop、没有工具、没有归档。后来为了"查重身份""更新已有档案"等需求，才在调用外面包了一个 `MAX_ROUNDS = 8` 的循环，并逐个打工具补丁：先加 `search_profiles`，再加 `get_profile`，随后补 `search_events / get_event`，最后加 `stage_person_update / stage_event_update`。每加一个功能就改三处：prompt 工具说明加一行、执行器 `else-if` 加一支、合并逻辑加一个数组。现在的 `intake-agent.ts` 就是这套补丁的沉淀：工具说明（99-109 行）、单工具调用约束（114-119 行）、执行器 else-if 链（234-283 行）、最终合并只认 `stagedPeople / stagedEvents` 两个数组（209-222 行）。**关系的读、查、暂存、修改从头到尾没有被补过，于是"关系"在 loop 里不存在。**

这不是"关系功能有个 bug"，而是循环本身没有按领域对象（人物/关系/事件/提醒/证据）设计工具面，补丁永远落后于领域模型。下面把结构性问题拆开写。

#### S1.1 工具面不对称（直接症状）

- **位置**：`src/lib/intake-agent.ts:99-109`（工具清单）、`:234-283`（执行器）
- **现象**：人物有 `search_profiles / get_profile / stage_person_update`，事件有 `search_events / get_event / stage_event_update`，**关系一个工具都没有**（无 search / get / stage）；`publicPerson`（125-147 行）返回的人物详情里也不含任何关系，提示词里的"已有档案"只给名字列表（`intake-panel.tsx:223-225`）。
- **对比**：通用问答智能体那边是另一条独立路线——有只读的 `get_relationships`（`recommendation-agent.ts:265-273`），但写侧 `update_person` 只管人物字段。两个 Agent 的工具集互不对称，也不共享同一套领域对象执行器，这是"补丁式"的直接证据。

#### S1.2 状态模型割裂：暂存数组与终稿 JSON 是两套真相

- **位置**：`src/lib/intake-agent.ts:176-177`（`stagedPeople / stagedEvents` 局部数组）、`:209-222`（最终合并）
- **现象**：
  - 工具路径产生的变更进 `stagedPeople / stagedEvents`，而关系只能靠终稿 `final.draft` 整包 JSON 出现，没有"暂存关系"这种中间状态；
  - 最终合并是 `[...stagedPeople, ...draft.people]`、`[...stagedEvents, ...draft.events]` 的**盲目拼接**，没有按 `targetPersonId / targetEventId` 做键合并，也没有去重；
  - 模型如果在 final.draft 里重复输出已经 `stage_*` 过的更新（提示只要求"不要重复"，没有机制保证），草稿页就会出现两条同人变更；
  - 终稿仍是"整包重写"，而不是"增量变更清单"，与工具路径的"暂存提案"语义并存，两套状态模型拼在同一轮循环里。
- **后果**：任何"先读已有关系、再产生关系变更"的工作流都无法表达——不是模型笨，是循环里根本没有这个状态槽。

#### S1.3 校验在循环外：一次 schema 违规 = 整个 job 报废，且没有回炉

- **位置**：`src/lib/intake-agent.ts:208-214`、`:216-222`（`parseIngestCandidate` 直接抛错，无 try/catch）；`:200-206`（只有 JSON 语法错误会回炉重问）
- **现象**：
  - 循环只对"JSON 语法/外壳格式"做一次纠错（`parseLooseJson` catch 后写 history 重问）；
  - 终稿一旦 JSON 合法但**内容违规**（例如 `closeness: "高"`、某个字段超长、relations 里多了个字段），`parseIngestCandidate` 的 `.strict()` 直接 throw，异常穿透 `runIntakeAgent` 抛给调用方——没有把校验错误反馈进 history 让模型修复的回合，100 个字段的草稿因为 1 个字段报废；
  - 关系规则 guard（`intake-panel.tsx:1078-1093`）只在用户点提交时执行，loop 内模型收不到"缺推断依据/依据格式错"的反馈，模型只能靠一次写对。
- **后果**：长材料/多家谱输入时，一次类型错误就前功尽弃；亲属推导越复杂，终稿字段越多，报废概率越高。

#### S1.4 历史上下文按"字符串尾部"截断，可能把 JSON 截成坏片段

- **位置**：`src/lib/intake-agent.ts:121-122`（`JSON.stringify(history).slice(-MAX_HISTORY)`）
- **现象**：`history` 是数组，却先整体 `JSON.stringify` 再 `slice(-8000)`。截断点落在任意位置时，提示词里的"已有工具结果"是一段**语法上不完整的 JSON 文本**；同时截尾部意味着旧轮结果整段丢失，模型对早期检索结果失忆。
- **建议**：先按"每条 tool result 独立序列化、逐条裁剪"，再拼数组，保证任何截断点都在条目边界上；或对旧条目做摘要而非丢弃。

#### S1.5 每轮一个工具 + 固定 8 轮，没有阶段划分

- **位置**：`src/lib/intake-agent.ts:114`（"每轮最多调用一个工具"）、`:12`（`MAX_ROUNDS = 8`）
- **现象**："检索本人 → 读档案 → 检索同名 → 读事件 → 查关系"这类常规核对要花 4-5 轮，且只读操作也严格串行；循环没有 plan / search / stage / verify 的阶段边界，模型要在同一个通用循环里混着做规划和执行；8 轮花完后直接抛"AI 在限定轮次内没有形成可确认的录入草稿"。
- **后果**：轮次预算被只读串行吃掉；遇到需要关系闭环的任务（读关系 → 改关系 → 校验）根本没有轮次可用。

#### S1.6 由此产生的用户可见后果

1. **任何 AI 窗口都无法"主动整理已有关系"**——录入 loop 看不见关系、无关系写入工具；问答智能体只有只读关系工具、无修改提案工具（本清单 S1.1）；
2. **跨材料联合推导不可行**——回归文档 3.3"追加已知贾政是贾母儿子 → 推贾敏↔贾政兄妹、黛玉→贾政舅甥"当前做不到；
3. **重复边与陈旧推断边**——loop 无合并去重，提交层再 `putRelation` 新建（S2）；
4. **一次字段错误整单报废**（S1.3），长家谱材料尤其容易触发；
5. **轮次浪费**（S1.5），复杂核对经常 8 轮耗尽。

#### S1.7 修复方向（分层，本次先不写代码）

**短期（比赛前最小补丁，8/31 前可完成）**：

1. 给录入 loop 补 `search_relations {query,limit}` / `get_relation {relationId}` / `stage_relation_update {relationId,changes}` 三件套，与人物/事件完全对称；`publicPerson` 增带该人的关系摘要（去敏：对方姓名、label、evidenceMode、confirmationStatus）；
2. 合并逻辑从"数组拼接"改为"按 `targetPersonId / targetEventId / relationId` 键合并 + 去重"；
3. `parseIngestCandidate` 失败不再直接抛出：把 zod 错误摘要写进 history，给 1-2 轮修复回合；
4. history 截断改为按条裁剪（先条后串）；
5. 把关系 guard（推断必有依据）前移到 loop 内，让模型在最终回合前就能收到关系校验反馈。

**赛后治本**：

1. **统一 ArchiveTool 注册表**：以领域对象为轴（person / relation / event / reminder / evidence），每个对象自动获得 search / get / stage / update 四类工具；`intake-agent` 与 `assistant-agent` 共用同一个执行器与同一份工具说明，彻底消灭两条补丁路线；
2. **阶段化 loop**：`plan（读材料定任务）→ search（读图：人物+关系+事件）→ stage（只产生增量提案，不再整包重写终稿）→ verify（JSON schema + 关系规则 validator 逐条反馈）→ commit（一次性事务：去重 + 写 `derivedFromRelationIds` + 基础边变更打回旧推断边）`，校验错误一律回炉而不是报废；
3. **亲属闭包下沉为确定性规则引擎**：模型只负责把材料标注成"明说边 + 称谓短语"，一/两步亲属推导（父子、祖孙、兄弟姐妹、叔侄姑侄舅甥姨甥、翁媳等）由本地规则引擎闭包计算并生成 `basis`，模型不再靠提示词心算——顺带解决 R1-R4 的规则覆盖问题，也让"推导关系"永远可复核、可重算。

### S2. 提交时关系不去重、不追链，重复边与陈旧推导边会积累

- **位置**：`src/components/intake-panel.tsx:1384-1421`（每条 relation 都 `putRelation` 新建）；`src/lib/face-db.ts:123-124`（`derivedFromRelationIds` 已定义但从未写入）
- **现象**：
  - 每次提交都生成新 `relationId`，没有按 `(fromId, toId, semanticKind/label)` 去重或合并；
  - `derivedFromRelationIds` 字段存在，但入库时从未填充。
- **后果**：
  - 同一句话录入两遍 → 两条重复边；
  - "贾母→贾赦/贾政"这类基础边被修改或删除后，依赖它推出来的"贾赦↔贾政 兄弟""贾母→宝玉 祖孙"不会失效、不会重新核验，图上留下陈旧推断；
  - 引荐路径（将来基于关系做"通过谁找贾母"）会踩到重复边或已失效边。
- **建议修法**（待确认）：
  1. 提交前查重：同 `(fromId,toId)` 且语义相同（`semanticKind` 或规范化 label）的边走更新（保留旧 `createdAt`、刷新 `updatedAt`），否则才新建；
  2. 推导边入库时写入 `derivedFromRelationIds`（依赖哪几条边推出来的）；
  3. 基础边增删改时，把依赖它的 `evidenceMode: "inferred"` 边批量打回 `confirmationStatus: "pending"`（或提示重新核验）。

### S3. 明说关系允许"无依据"入库，审计锚点可缺失

- **位置**：`src/lib/intake-draft.ts:255-268`（`basis` 为 `shortText`，即 optional）；`src/components/intake-panel.tsx:1078-1093`（guard 只拦"推断且无推断依据"）
- **现象**：模型若给"原文明说"的关系漏填 `basis`，zod 解析通过，提交 guard 不拦，入库后 `basis: undefined`。
- **后果**：明说边与推断边一样失去原文锚点，溯源面板无法展示依据，审计性下降。
- **建议修法**（待确认）：`ingestRelationSchema` 把 `basis` 改为必填 `z.string().max(500)`（至少对 AI 抽取路径）；guard 增加"AI 抽取的关系必须有 basis"校验，人工手填可豁免。

### S4. 长草稿可能把材料挤成 0 字符

- **位置**：`src/lib/intake-draft.ts:404-420`（`fitPromptMaterial`）
- **现象**：前缀 = 基础规则 + SCHEMA + 已有档案（最多 1000 字）+ 上轮草稿 JSON，上限 11,800 字符；函数先 `prefix.slice(0, max)` 再给材料分剩余额度。
- **后果**：上轮草稿很大时（多人物/多事件/多关系），`max(0, 11800 - prefix.length)` 为 0，本轮材料整体丢失，模型只能"基于空材料"输出（或空草稿/编造）。对亲属材料而言，长家谱分批补录时尤其容易触发。
- **建议修法**（待确认）：给材料保底额度（如最少保留 3,000 字符，优先截断"上轮草稿"和"已有档案"，不截规则与材料）；或上轮草稿按条目降采样后再注入。

| 编号 | 缺口 | 会失败的回归样例（`doc/quality/亲属关系推理-红楼梦测试样例.md`） |

**建议修法**（待确认，最小补丁）：
- `KINSHIP_RULES_ZH` 增补两条一步推导规则：
  1. 父母/祖辈的兄弟/姐妹 → 叔伯姑舅姨；其子女与我 → 侄/甥（侄系/甥系）关系，祖辈放 from；
  2. 配偶的父/母/兄弟/姐妹 → 翁媳/婆媳/岳婿/叔嫂/姑嫂等姻亲，一律标"姻亲"，不得标血亲；
- 曾祖链：允许"祖辈链连续两跳以上"时输出"曾祖孙"（仍 0.5–0.75 置信、标注推断），或明确在回归文档中降级为"不支持"（二者选一，避免规则与测试打架）；
- 继亲/族亲：补"继母/继父的子女 → 继姐妹/继兄弟（无血缘）"；"同宗"输出"族兄弟（推断）"且不得写成亲兄弟。
