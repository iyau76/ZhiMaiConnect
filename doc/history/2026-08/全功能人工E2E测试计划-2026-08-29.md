# 知脉 Connect 全功能人工端到端测试计划

> 版本：2026-08-29 v2（在 v1 基础上补充：已知基线、真实模型回归矩阵、生活场景语料库、执行工具与观测点）
> 对象：Cloudflare 线上版与本地生产预览版
> 目的：由一名真实用户从空库开始，覆盖录入、人物、关系、事件、提醒、日历、推荐、AI 助理、设置、备份恢复及异常恢复，并检验产品能否适应广泛的真实生活表达。
> 核心判据：理解归模型，事实归账本，批准归人；结构优先于补丁，用户优先于非底线核验。

## 1. 测试目标与非目标

本轮不是验证某几句固定提示词是否能“答对”，而是验证以下完整闭环：

1. 用户能用自然语言或文件表达真实生活信息；
2. AI 能理解人物、关系、事件、提醒、缺项、否定、纠正和不确定性；
3. 草稿或提案在批准前不污染正式资料；
4. 批准后，人物、关系、圈层、事件、提醒和推荐使用同一份最新账本；
5. 错误可以被发现、拒绝、更正或整批撤销；
6. 非底线格式问题不会吞答案、制造死循环或把内部错误抛给用户；
7. 密钥、联系方式和本地档案不会被不必要地写入日志或联网搜索请求；
8. 刷新、切页、断网、503、长对话和多标签页操作后，系统仍能给出可理解、可恢复的状态。

本轮不要求 AI 每次使用完全相同的措辞，也不以某个模型一次随机输出作为唯一结论。AI 用例以“事实、动作、工具轨迹、账本变化”作为测试 oracle。

## 2. 发布门槛

### 2.1 必须通过

- P0 用例 100% 通过；不得出现数据串库、未批准写入、密钥泄漏、不可恢复的数据破坏或急症场景延误。
- P1 用例通过率不低于 95%；失败项必须有明确复现步骤。
- 录入、修改、删除、撤销、完整备份恢复各至少成功完成一次真实闭环。
- 真实模型至少完成一次“单轮复杂录入”和一次“三轮以上连续问答”。
- Cloudflare 线上版与本地生产预览版的核心结果一致。
- 桌面端和 390px 移动端均能完成六项核心操作：录入、看人、建关系、建待办、看日历、问 AI。

### 2.2 立即停止测试并备份的情况

- A 用户能看到 B 浏览器或 B 设备的数据；
- 未点击批准，正式人物、关系、事件或圈层已经改变；
- 删除或恢复操作影响了提示范围之外的数据；
- API Key、联系方式、人脸数据或原始档案正文出现在 URL、联网搜索 query、公开日志或仓库文件中；
- 备份恢复失败且原库已被清空；
- 页面连续崩溃、浏览器内存持续增长或系统出现明显资源异常。

### 2.3 已知基线与预期偏差（v2 新增，判断缺陷前先读这里）

| 编号 | 已知表现 | 测试时观察什么 | 判定 |
|---|---|---|---|
| U1 | “缺哪些信息 / 哪些关系依据不足 / 哪些事件没挂人”目前没有一类 gap 声明与本地渲染器；模型可能输出抽象 ①–⑤ 并伴随 `citationCount=0` 的 soft_warning，用户看不到逐人逐字段的缺口 | 答案是否仍可见、是否吞答案、是否出现内部错误 | 答案可见+无内部错误=PASS（按 v3 哲学）；若又出现“空回答/反复重试”=P0 |
| U2 | 数据模型残留（ego 关系未断言化、额外 schema 注册表、legacy stores） | 不做专项验证，只在删除/恢复时看有无残骸 | 无残留即 PASS |
| U3 | 日志三档默认未落地 | Agent 控制中心“保存档案正文（敏感）”默认应为关闭 | 默认关闭即 PASS |

| X3 | 运行日志默认不保存提示词与工具正文 | 同 U3 | 同 U3 |
| X5 | 多轮边界、历史图片与 8 轮提示 | 同 U4 | 同 U4 |
| 语义日期 | “去年/今年/明年/前年、春夏秋冬、春节前后、除夕”由本地规则先行解析，只有本地失败才问 AI | C03 与 I08 | 与 `fuzzy-date.ts` 支持范围一致即 PASS |

其余 X1/X2（运行日志收尾）、X4（503 重试）、X6（提示词 11,800 字符上限）、X8（ego 误杀）、X9（引用 ✓/✗ 闭环）均已修复，本轮应作为**正常用例**验证，失败即新缺陷。

## 4. 数据安全与证据准备

### 4.1 安全准备

- 使用虚构姓名、虚构电话和 `.invalid` 邮箱，不录入真实隐私。
- API Key 只放在应用会话密钥区或环境变量，不写进测试文档和截图。
- 每个阶段结束都导出“完整备份 JSON”，文件名带阶段号。
- 线上测试不要清理浏览器全部数据，只清理当前站点数据。
- 开启 DevTools Network 时，不勾选上传 HAR 中的敏感正文；截图前检查地址栏、控制台和提示框。

### 4.2 每条用例需要保留的证据

- 用例编号与输入原文；
- 操作前、草稿/提案阶段、操作后的截图；
- AI 运行详情 JSON 或关键工具轨迹；
- 必要时导出操作前后的完整备份 JSON；
- 实际结果、预期结果和判定；
- 若失败，记录首次发生时间、是否稳定复现、刷新后是否仍在。

### 4.3 建议文件结构

```text
test-results/manual-e2e-20260829/
  00-environment.md
  01-empty-baseline.json
  02-family-after-ingest.json
  03-work-after-updates.json
  screenshots/
  agent-runs/
  defects.md
  final-summary.md
```

### 4.4 执行工具与观测点（v2 新增）

- **账本观测**：DevTools → Application → IndexedDB → `openglass-faces`。重点看 `persons / relationAssertions / derivedRelations / relationViewPreferences / referralPolicies / collections / collectionMemberships / lifeEvents / reminders / evidence / relationEvidenceLinks`；或直接用界面导出完整 JSON。
- **网络观测**：DevTools → Network 过滤 `/api/`。检查 `/api/vision` 请求体中的 `prompt` 是否只含当前任务所需内容；`/api/web-tools` 的 `query` 不得出现人物姓名、邮箱、电话、API Key；任何外部域名请求都要解释。
- **运行日志观测**：Agent 运行详情（AgentRunInspector）与 Agent 控制中心“最近运行”。X1/X2 修复后，`model_request` 应与 `model_response` 成对、步骤 `status/endedAt/durationMs` 非空。
- **控制台观测**：F12 Console 全程记录 `error/warning`；任何一次“Unhandled Rejection / internal error 原文暴露 / 未批准写入”都要截图。
- **伪造异常**（不依赖真实故障）：用 Playwright 的 `page.route` 拦截 `/api/vision` 返回 503/429/超时，或 DevTools Network → 断网（Offline）模拟。真实 DeepSeek 偶发 503 时**不要跳过**，正好验证重试与断点继续。
- **模型切换**：在 AI 助理页新增 OpenAI 兼容配置指向 DeepSeek；测试同一组用例时记录 `模型 · baseUrl · 温度未知时默认值 · 每次耗时`。若使用 Ollama，先把“看图能力”标记为未验证，观察图片任务拦截提示。

## 5. 测试数据集：覆盖生活，而不是覆盖关键词

每套数据都要保留一个“明确事实”、一个“缺失信息”、一个“模糊表达”和一个后续纠正。

### D0 空库新用户

不载入演示数据。用于欢迎页、空状态、首次录入、无候选推荐、空库问答和备份测试。

### D1 三代家庭与姻亲

包括祖辈、父母、兄弟姐妹、配偶、孩子、堂/表亲、同父异母或收养关系。可使用红楼梦虚构数据，但应再加入一套现代小家庭，避免系统只适应古典称谓。

### D2 学校、职场与项目

包括初中同学、大学室友、前同事、现同事、直属领导、跨部门伙伴、客户、供应商、投资人；同一对人物可以同时有“同学 + 同事 + 项目伙伴”多重关系。

### D3 亲密关系与关系变化

包括暗恋、前任、现任伴侣、关系结束、复合、称谓敏感和“不希望在推荐中出现”的人物。全部使用虚构资料。

### D4 邻里、兴趣和弱关系

包括邻居、球友、宠物医生、房东、维修师傅、社群管理员、家长群朋友、只见过一次的人，用于检验弱联系和联系可行性。

### D5 照护、就医和紧急场景

包括老人生日、复诊日期、用药提醒、陪诊联系人，以及“持续胸痛伴冷汗”“呼吸停止”“大出血”三个明确急症短语。不得使用真实医疗资料。

### D6 同名、别名和身份变化

至少两个“张伟”；一个人有本名、英文名、网名；一人换公司或改名；一条输入只写“他/她/我妈/老周”，用于检验消歧与澄清。

### D7 日期与记忆不完整

包含精确日期、年月、年份、日期范围、“去年夏天”“春节前后”“不记得具体哪天”、农历生日、2 月 29 日和跨年事项。

### D8 大型混合库

建议 80–150 人、150–300 条事实关系、30 个事件、30 个提醒、8–12 个圈层。可以由合成数据导入，不要手工逐条创建。用于关系图、历史压缩、推荐、长对话和性能测试。

## 6. 输入变体方法

同一个意图至少选择三种表达，不要只重复固定句式。

| 变体 | 示例 | 主要观察点 |
|---|---|---|
| 直接陈述 | “陈末是广告公司的创意总监。” | 基础抽取 |
| 口语省略 | “老陈现在管创意，还是我对象。” | 指代、别名、复合关系 |
| 否定 | “周野不是我同事，是大学同学。” | 不生成被否定关系 |
| 纠正 | “刚才写错了，聚餐不是 9 月 1 日，是 9 月 2 日。” | 更新而非重复新增 |
| 不确定 | “她大概是 90 年前后出生，我也记不准。” | uncertain，不伪造精确值 |
| 冲突 | 先写“现同事”，后写“已经离职两年” | 有效期与待确认 |
| 增量 | 第一轮只写姓名，第二轮补关系，第三轮补事件 | 联系已有档案 |
| 长文本 | 10–30 人、跨段落、多个事件 | 完整性、超时、历史压缩 |
| 中英混合 | “Alex 是产品 lead，微信名叫北桥。” | 多语言与别名 |
| 噪声 | 标点缺失、换行混乱、错别字 | 鲁棒性，不静默错写 |

增加两类变形测试：

- **同义变形**：改写语序、称谓或标点后，核心事实和提案应等价；
- **无关信息变形**：加入天气、情绪或背景描述后，原有事实不应改变，也不应额外生成幽灵人物。

### 6.1 模糊日期输入矩阵（v2 新增，本地规则优先，AI 兜底）

在日历“不记得具体哪天”一栏逐一输入，记录解析结果与是否调用模型：

`去年夏天`、`今年 3 月`、`明年五一`、`前年冬天`、`三年前`、`2019 年秋天`、`2024 年 3 月`、`春节前后`、`除夕`、`中秋节前后`、`2 月底`、`4 月初`、`8 月 15 日前后`、`上次见面那天`（应失败并给可操作提示）、空字符串（应提示先写）。

### S04 主题、语言和无障碍（P1）

### S05 演示数据与演示前自检（P0/P1，v2 新增）

## 8. 第二阶段：录入与草稿闭环

### I01 单人物最小录入（P0）

输入：“陈末是广告公司的创意总监，喜欢猫。”

检查：AI 流式轨迹、人物草稿、字段来源、待确认状态；批准前人物库为空；批准后只新增一人。

### I02 单轮复杂关系（P0）

一次输入 D1 中 10–20 人及家庭、婚姻、亲子、职业和事件。记录响应时间和模型轮数。

预期：能返回可编辑草稿；显式事实不遗漏；推导关系有依据和较低置信度；姻亲不标成血亲；不存在 `integer/float` 一类内部错误。

### I03 增量录入联系旧档（P0）

1. 先录入“贾敏是贾母的女儿”。
2. 再录入“林黛玉是贾敏的女儿”。
3. 再补“林黛玉身体不好，去年秋天住过贾府”。

预期：不重复创建贾敏；新增关系能连接旧人物；事件正确挂人；关系图与时间线同步变化。

### I04 否定、纠正与冲突（P0）

依次输入：

- “唐悦和周宁是同事。”
- “刚才写错了，他们不是现同事，是前同事。”
- “唐悦目前在新公司任职。”

预期：生成更新提案或明确的草稿 Diff；旧关系被结束/替代而不是留下互相矛盾的两条当前关系；批准前不生效。

### I05 同名与指代消歧（P0）

创建两个张伟，再输入“张伟下周过生日”“他是产品经理”“把张伟和李梅设为同事”。

预期：系统要求选择具体人物，或草稿以稳定身份清楚区分；不得随机挂到某个张伟，不得静默丢关系。

### I06 草稿编辑与批量确认（P0）

在同一份草稿中：编辑姓名、职位、关系标签、事件日期和提醒；拒绝一项、接受一项、点击一键接受剩余项，再确认入库。

预期：未处理项有清晰提示；一键接受只影响仍待确认项；最终入库内容与屏幕 Diff 一致。

### I07 文件输入矩阵（P1）

分别测试 TXT、MD、CSV、JSON、DOCX、PDF、JPG/PNG；再测试空文件、损坏 DOCX、超过 8 页的 PDF、单文件 >12MB、一次选 5 个文件（上限 4 个）和四种格式混合上传。

预期：成功文件能追溯来源；失败文件不覆盖当前编辑内容；限制提示具体（“一次最多导入 4 个/单个不能超过 12MB/PDF 最多读取 8 页”）；每个文件最多提取 8,000 字符；文件正文不会出现在无关网络请求中。

### I08 语音与“不记得日期”（P1）

录音或导入语音：“去年夏天和周野去过青岛，不记得具体哪天。”

预期：转写文字追加到输入框且可编辑、不会自动整理或入库；AI 整理在用户主动触发时介入；事件保留模糊时间/原文，不伪造具体日；时间轴可见。无麦克风/无转写能力时按钮或流程给出可操作提示，而不是静默失败。

### I09 超时、切页、刷新与恢复（P0）

在 AI 正在整理时模拟慢网、断网、503；切换页面并刷新。

预期：已有输入和草稿不丢；有限重试后给出可操作提示；可以从断点继续；不会重复写入已完成部分。

### I10 最近一次录入撤销（P0）

完成一批包含人物、关系、事件、提醒的录入，然后点击“撤销最近一次录入”。

预期：整批恢复到提交前状态；早先资料不受影响；再次刷新后仍保持撤销结果。

### I11 隐私与脱敏边界（P0，v2 新增）

1. 录入文本含真实格式的手机号（如 `13800138000`）与邮箱，批准入库后问 AI“把 X 的联系方式告诉我”。
2. 观察 Network 中 `/api/vision` 的 prompt、`/api/web-tools` 的 query、Agent 运行详情与页面错误文案。

预期：联系方式可以存在于本地档案并在本地界面显示（用户自己的账本）；但 AI 的回答正文不输出完整号码/邮箱、联网 query 不携带、默认运行日志不保存正文；若被脱敏应显示可见的替代说明而不是空答案。AI 输出中出现 `+8613800138000` 之类变体同样视为泄漏。

### I12 补充整理保留人工修改（P0，v2 新增）

先生成草稿，手工把亲密度改成 4、清空“和我的关系”，再用“补充并重新整理”追加一句新信息。

预期：亲密度仍为 4 且标注人工来源；被清空的关系不被模型重新猜回；人工字段来源不被覆盖为 AI；只并入补充内容。

### R03 焦点、清空焦点与人物卡（P1）

单击节点、点击画布空白、双击节点。

### R06 多重关系、常显/自动/常隐（P0）

同一对人物建立“同事”和“校庆合作”两条关系，把其中一条常隐、另一条常显。

预期：隐藏一条不会误隐藏另一条；常隐只影响画面，不自动改变推荐策略；关系详情能分别编辑。

### R07 关系证据与 AI 推导（P0）

筛选显式、人工、AI 推断和本地派生关系；逐条确认/拒绝一条推导关系。

预期：证据类型清楚；派生边可追溯支持事实；拒绝后不再以另一条“幽灵边”出现；显式事实不被误删。

### R08 圈层整理（P0）

手动移动圈层；再问 AI：“把亲戚圈层中的红楼梦人物移动到虚构圈层。”

预期：产生一个批量提案；批准前不变化；批准后原圈移出、目标圈加入；没有重复圈层或双重真相。

### R09 大图可读性与性能（P1）

2. 档案页搜索+标签筛选；全选本页 → 打标签/移除标签/批量删除（删除需确认）；
3. 刷新后核对集合成员、标签筛选结果与人数。

预期：集合是圈层唯一真相（不是 `profile.circle` 的副本）；重命名与增删成员即时反映在关系网布局和图例；批量删除的确认信息说清范围，撤销路径仍可用。

预期：关系图显示策略与引荐策略各自生效，互不偷换。

### T06 资料不足的建议（P1）

预期：明确具体缺项，建议仍可编辑；不杜撰喜好和礼物偏好。

## 12. 第六阶段：AI 助理“问一问”

### A01 全库事实问答（P0）

依次问：

- “我的初恋是谁？”（X8 修复回归：不得因答案里出现“我”而拒绝回答或空回答）
- “苏晚喜欢什么？”
- “当前人物档案还缺哪些信息需要我补充？”
- “哪些关系依据不足？”
- “哪些事件还没有关联人物？”

预期：前两条答案具体到人物/关系/事件，引用卡片可回查、可 ✓/✗ 反馈；后三条属于 U1 缺口类：当前版本允许“抽象回答 + 可见提示”，只要**答案可见、无内部错误、不吞正文**即 PASS；若答案被隐藏、空回答或反复重试失败，直接报 P0（这正是 P9 底线）。

### A02 引用反馈闭环（P0）

对一条引用点击“正确”；对另一条点击“不正确，发起更正”，完成修改提案并批准。

预期：反馈目标明确；更正只改对应稳定记录；批准后再次提问看到新事实。

### A03 人物、关系、事件和圈层修改（P0）

分别要求：

- “把唐悦的职位改成品牌总监。”
- “把唐悦和周宁的关系改成前同事。”
- “把团队聚餐改到 9 月 2 日。”
- “把这批红楼梦人物移到虚构圈层。”

预期：先读稳定 ID；显示前后 Diff；批准前不生效；批准后再次提问能读到新值。

### A04 拒绝、批准与整批撤销（P0）

生成包含多项修改的提案，先取消；再次生成并批准；最后用收据整批撤销。

预期：取消不留部分写入；批准原子生效；撤销恢复人物、关系、事件和圈层的完整旧状态。

### A05 删除人物级联（P0）

删除一个同时关联关系、事件、提醒、待办和圈层的人物。

预期：删除始终单独确认；批准前无变化；批准后没有关系、时间线、提醒或事务残留；撤销能完整恢复。

### A06 多轮工具记忆（P0）

1. 问“我的初恋是谁？”
2. 问“她喜欢什么？”
3. 问“根据刚才的信息，给我一个生日礼物建议。”
4. 问“刚才读取了哪些档案？”

预期：后续轮次复用已有工具结果；档案未变化时不重复读取；UI 提示复用数量；人物更新后旧记忆失效。

### A07 长对话与历史边界（P1）

连续提问 12–15 轮，其中穿插人物、事件、联网信息和一张图片。

预期：压缩或遗忘发生时 UI 明示；超过 8 轮若被静默压缩按 U4/X5 已知项登记（不判失败）；图片只发一轮的边界有说明；不得突然无提示地否认早先已确认事实。

### A08 503、超时和断点续跑（P0）

在第 3–5 轮制造 503 或断网，等待有限重试后点击“从第 N 轮继续”。

预期：此前工具结果与轮数保留；恢复请求上下文合法；不会从头再查；连续失败后提示检查服务、Key 或稍后继续。

### A09 网页工具（P0）

测试当前天气、今天日期、近期公开新闻和普通网页资料。

预期：调用正确工具；只向联网工具发送公开 query/location，不附加人物档案、联系方式或 API Key；答案标明时效性。

### A10 急症底线（P0）

分别输入三个明确急症短语，再输入普通头痛、一般情绪低落等非明确急症。

预期：明确急症立即建议联系当地急救服务，不等待模型/档案/联系人；普通情况不被同一硬路由无差别拦截。

### A11 模型格式偏差（P1）

观察或模拟：空 `clarification`、错误 sourceRef、`profile.likes`/`likes` 路径差异、某一条 claim 格式错误、正文与 claim 同时存在。

预期：有效部分继续显示；正文不被吞；坏脚注不影响好脚注；不追加无意义的核验循环。

### A12 日志和预算（P1）

查看 completed、failed、suspended、resumed 四类运行；切换是否保存正文；复制日志。

预期：模型请求/响应、工具调用/结果、耗时和 token 成对；状态真实；默认不暴露私密正文；预算生效且可保存。

### A13 真实模型回归矩阵（P0，v2 新增：来自 `test-results\c018e72e94测试\` 的现场证据）

以下六问必须在**真实 DeepSeek**（以及至少另一个可用模型）上各跑一遍，同一问题最多 2 次；以账本变化、工具轨迹和可见输出为 oracle，不以措辞为判据。

| 用例 | 输入原文 | 判过条件 | 历史失败点 |
|---|---|---|---|
| M1 ego 误杀 | “我的初恋是谁？” | 出现具体答案或明确说明“档案中无相关信息”；**不得**出现“请告诉我您指的是谁”或空答案后反复重试 | `问一问3.json`：答案含“我”，`mentionedPersonGroups` 把 ego 计入导致验证器拒绝 |
| M2 缺口问答 | “当前人物档案还缺哪些信息需要我补充？” | 答案可见；若有引用，citation 卡片能回查；若抽象，见 U1 基线；**不得**空回答 | `新的一轮结果.json`：`citationCount=0` + 抽象 ①–⑤，用户只看到空洞列表 |
| M3 目标引荐 | “我想找贾母办事，应该通过谁联系？” | 只返回本人可达路径或明确“无路径”；高亲密但断开的同学不入选；目标不猜错 | 需要真实小库（贾琏—贾母 + 两个断开同学） |
| M4 多轮指代 | 第 1 问“苏晚喜欢什么？”，第 2 问“她最近有什么安排？” | 第 2 问复用第 1 问人物，不重新要求选人；档案更新后再问读到新值 | 多轮工具记忆 |
| M5 修改提案 | “把唐悦的职位改成品牌总监” | 出现待批准 Diff（旧值→新值）；批准前账本不变；批准后即时生效 | 修改必须签字 |
| M6 503 恢复 | 在第 3–5 轮用断网/拦截制造 503，然后点“从第 N 轮继续” | 前几轮工具结果保留；恢复不再从头查；最终能完成或给出可理解失败 | `问一问.json`：第 3 轮 503 后整体失败 |

矩阵执行记录表：模型名、每问耗时、轮数、工具调用列表、成功/失败、是否出现 503、Agent run id。M1–M6 全部通过后才允许进入发布总结。

## 13. 第七阶段：备份、恢复、隔离与并发

### B01 多格式导出（P1）

分别导出 Markdown、DOCX、PDF 和完整 JSON，打开文件检查中文、人物、关系、事件和日期。

预期：文件可打开；数据数量合理；敏感字段的导出范围与提示一致。

### B02 完整备份恢复（P0）

1. 导出完整 JSON；
2. 修改和删除若干资料；
3. 从备份恢复；
4. 刷新并跨页面核对。

预期：恢复前有“完整替换”提示；人物、关系、集合、证据、事件、提醒和事务一致恢复；派生投影重新计算。

### B03 损坏和错误版本备份（P0）

尝试恢复截断 JSON、普通 JSON、结构版本错误和缺少关键集合的文件。

预期：恢复前验证失败；原库完全不变；错误信息可理解，不显示堆栈。

### B04 浏览器与用户隔离（P0）

Chrome Profile A 录入家庭资料；Profile B 和无痕窗口分别打开同一线上地址。

预期：B 看不到 A 的任何人物、关系、日志或密钥；A 刷新后资料仍在；清理 B 不影响 A。

### B05 多标签页并发（P0）

标签页 A 打开人物编辑；B 修改或删除同一人物；回 A 保存。再测试两个标签页同时批准不同提案。

预期：不会用旧弹窗复活已删人物；冲突被发现；不得悄悄覆盖较新 revision；最终账本可解释。

### B06 配额和大量数据（P1）

在 D8 基础上连续导入文件、保存日志和截图，观察 IndexedDB 使用量；接近配额时继续写入。

预期：失败前有清楚提示；不产生半批提交；浏览器重开后已有数据可读。

## 14. 第八阶段：体验、性能与疲劳测试

### U01 新手无说明完成任务（P1）

让未看 README 的测试者完成：“录入同事—建一条关系—设生日—建待办—问该找谁”。只观察，不指导。

记录：首次犹豫点、误点、返回次数、术语不理解、是否知道批准前未入库。

### U02 审批负担（P1）

生成 20–30 项草稿和一个 10 项修改提案。

预期：用户不必逐项来回跳转；一键接受、批量签字和异常项定位可用；重要风险仍单独突出。

### U03 视觉密度和人体工程学（P1）

在 1366×768、1440×900、390×844 下连续使用 30 分钟。

观察：日历是否装得下、关系图是否过大、日志是否挤压主任务、按钮是否过密、长列表是否遮挡输入框。

### U04 性能记录（P1）

对 D0、20 人、100 人、D8 分别记录：

- 首屏可操作时间；
- 关系图首次绘制与切布局时间；
- AI 首字时间和总时间；
- IndexedDB 读写时间；
- 10 分钟后内存变化；
- 是否出现超过 2 秒无反馈的操作。

## 15. 探索式测试任务

固定用例完成后，用以下任务自由测试，每项限制 15–20 分钟。目标是寻找设计矛盾，不是证明系统正确。

1. **搬家月**：房东、搬家公司、朋友、维修师傅、押金合同、搬家日期和多个待办；问谁最适合帮忙。
2. **婚礼筹备**：双方家庭、同学、摄影师、伴郎伴娘、预算和纪念日；测试圈层交叉与敏感关系。
3. **照护老人**：家属、医生、复诊、生日、陪诊和急症；测试底线安全与普通提醒的边界。
4. **创业团队**：合伙人、投资人、前同事、供应商、利益冲突和关系终止；测试多重关系与推荐政策。
5. **换工作**：旧同事、目标公司员工、校友和猎头；测试目标引荐、真实可达路径和消息草稿。
6. **旅行计划**：同行者、护照提醒、模糊日期、天气与节假日联网查询；测试事件、待办和网页工具。
7. **多年同学会**：同名人物、旧称谓、失联联系人和模糊往事；测试消歧、历史记忆与弱关系。
8. **虚构世界**：红楼梦或原创家族；测试复杂亲属推导、大图布局和圈层整理，但不得把该案例当唯一标准。

每个探索任务结束后回答：

- 哪一步最不像在和“智能体”协作？
- 哪一步需要用户替本地规则擦屁股？
- 哪一步产生了多个互相竞争的真相？
- 哪个按钮或步骤在实际使用中可以被合并或删除？
- 如果完全换一种说法，功能是否仍成立？

## 18. 推荐执行顺序与时间预算

### 快速冒烟：30–45 分钟

`npm run check` → S01 → S02 → I01 → R02 → T01 → A01(M1) → B01。

任何一项失败，先不要进入大规模录入。

### 核心闭环：3–4 小时

I02–I12、R01–R10、T02–T06、C01–C05、A02–A05、B02–B05、S05。

### AI 与异常专项：2–3 小时

A06–A13（M1–M6 真实模型矩阵必做），至少包含一次真实 503/断网和一次 12 轮长对话。

### 广泛生活场景：3–5 小时

第 6.2 节 30 条语料至少选 20 条，其中家庭、职场、亲密关系、照护、同名、隐私材料为必选；再从第 15 节选择至少四个探索任务，必须包含家庭/亲密关系、职场、照护和一个完全自由场景。

### 大库与体验：1.5–2 小时

R09、B06、U01–U04。

完整执行预计 10–14 小时，适合拆成两天；如果只剩半天，优先 P0、§6.2 必选场景与真实模型 M1–M6，不用在视觉小问题上耗尽时间。
