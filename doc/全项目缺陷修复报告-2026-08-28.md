## 1. 结论

扫描列出的 31 项问题已经全部关闭。修复不是把错误提示换个说法，而是集中处理了六个结构性根因：

1. 录入对象没有稳定身份，提交阶段又按姓名重新解析；
2. Agent 工具、暂存状态和终稿存在多套真相；
3. 关系语义、推导依据和依赖失效没有统一领域层；
4. 推荐把模型输出误当排序真相；
5. IndexedDB 批处理、级联和回滚缺少事务边界；
6. 生产 API 安全控制停留在单 isolate 内存状态。

本轮将这些能力分别下沉为稳定草稿 ID、领域工具注册表、关系语义/亲属闭包引擎、确定性本地排名、跨 store 事务，以及 Cloudflare 边缘限流 binding。UI 只负责展示与确认，不再承担隐式数据修复。

## 5. 关键架构结果

### 5.1 录入现在只有一套变更真相

人物、关系、事件都通过同一领域工具注册表读取与暂存。模型可以批量调用工具，但只能形成候选变更；候选进入统一草稿，由用户接受/拒绝。最终提交先解析所有引用并构建批次，再由 IndexedDB 事务一次写入。任何歧义或写入失败都不会留下半批数据。

### 5.2 关系推断可解释、可失效

显式关系和推断关系分轨保存。推断必须携带 basis、较低 confidence 与基础边依赖；本地引擎只执行有白名单的亲属闭包。基础边修改、删除或孤儿清理后，下游推断自动回到待确认并退出推荐。

### 5.3 AI 不再拥有排序权

开放求助和目标引荐都由本地算法生成最终候选。目标模式只返回真实可达路径；关系边是否显示与能否用于推荐是两套独立策略。模型工具可以逐渐读取必要档案并生成解释，但无法新增候选、交换顺序或改分。

### 5.4 安全边界进入部署配置

会话校验、大小限制、SSRF、首包/SSE 验证留在应用层；请求频率由生产构建生成的 Cloudflare bindings 在边缘执行。绑定标识不是密钥，可以纳入版本控制；真正的模型密钥仍只通过 Cloudflare Secret 管理。
