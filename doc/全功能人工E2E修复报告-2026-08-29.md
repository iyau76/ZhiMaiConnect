## 二、结构性改进

### 2.1 未入库草稿成为可寻址工作区

此前，未提交草稿只有一次模型输出中的 `plan:*` 临时引用。补充整理时，模型看到的是一份文本快照，无法稳定更新原草稿，因而会使用空 ID、旧 `plan:*` 或重新创建重复记录。

现在增加了正式的 intake workspace：

- 每条人物、事实、关系、事件、提醒和证据都有稳定 `draft:*` 引用；
- 工作区带 revision，补充轮次生成 update/delete/create，而不是重新生成一份互不相识的草稿；
- `plan:*` 在首轮编译后统一重绑定为 `draft:*`；
- 人工编辑字段、人工来源、身份决策和关系核对状态在后续补充中保留。

真实 API 结果：先生成“唐悦和周宁是同事”，不入库，再补充“刚才写错了，是前同事”，一轮完成原关系更新，没有重复人物、重复边或旧值残留。

证据：`test-results/live-adversarial/2026-08-29T08-59-46-595Z.json`。

### 2.2 关系从展示标签收敛到稳定语义身份

关系本体现在统一完成以下编译：

- 人物性别事实决定父母/子女角色，不再由模型措辞决定 `son` 或 `daughter`；
- “丈夫”“妻子”只作为展示语言，不再成为对称配偶关系的方向性身份；
- “妾”保留为关系级的 concubinage 区分；
- “继母的女儿”不会再被误判为 `step_parent_of`，而是识别为继同辈语义；
- 姑母、叔父、舅父、姨母、内侄等称谓统一进入关系本体；
- 本地投影仍只消费已确认事实断言，生成结果不回灌规则输入。

因此，同一事实即使模型分别输出“女儿”“母亲-女儿”，或“丈夫”“妻子-丈夫”，持久化语义身份也保持一致。

### 2.3 证据核验退出 Agent 重生成循环

一次真实失败揭示了明确的性能根因：模型首轮已在约 15 秒内返回完整的 54 项计划，但 basis 对原文做了轻微压缩。本地把“没有逐字复制”当作硬错误，要求模型重新输出整份计划；第二轮因长度截断又触发第三轮，最终耗尽 8k 输出 token。

现改为：

- ID、任务结构、日期格式和事务一致性仍是硬契约；
- basis 措辞、未对齐证据、模型推导和多跳称谓属于非底线核验；
- 本地优先把模型改写的 basis 对齐到同时包含关系两端与关系线索的原文片段；
- 无法对齐时保留草稿，并显示“AI 生成，请注意辨别”的具体原因；
- 不再为非底线核验重新生成整份计划，不吞掉结果，不抛内部错误给用户。

这落实了 `中期反思.md` 的 P8/P9：结构问题由结构承载，非底线核验只能成为可见提示，不能成为收费站。

### 2.4 “问一问”的输出与工具语义

助理输出已采用类型化声明：

- `fact`：档案事实与引用；
- `gap`：具体人物、具体字段的缺失；
- `advice`：建议；
- `language`：普通语言回答；
- `uncertain`：资料不足或未核验内容。

`search_profiles` 现在明确返回 projection、returnedFields、omittedFields 和 detailTool。摘要工具没返回 likes，不再等价于“likes 为空”；字段级问题需要升级到详情读取。即使声明无法验证，内容也会落到“AI 生成内容（请注意辨别）”，不会静默消失。

真实 grounding/memory 场景已通过，证据见 `test-results/live-adversarial/2026-08-29T08-31-08-088Z.json`。

## 三、体验与数据闭环改进

- 月精度事件使用月份控件，年精度使用年份控件，不再强迫用户选择某一天。
- 事件增加原始时间表述；“去年夏天”等文本由本地模糊日期解析器生成范围并保留原文。
- 待确认内容改为软提醒；用户可直接入库，未接受的 AI 关系以 pending 保存且不参与亲属投影。
- 补充整理保留人工修改和人工来源，不会被后一轮重新标成 AI。
- 同名人物和重复展示项使用稳定草稿/记录 ID 作为 React key。
- 英文界面的关键控件、提示、日历和设置文案已补齐。
- E2E 的事件更新用例现在等待事务完成再读取 IndexedDB，消除了并发回归中的读取竞态。

## 四、Cloudflare 性能改进

Worker 的 `/api/vision` 已从“逐 SSE chunk 解码、解析、重组、再编码”改为：

1. 完成请求校验与上游请求；
2. 收到上游响应头后，直接转发原始字节流；
3. 仅记录请求字节数、首响应头耗时、总墙钟时间、状态与流量等结构化指标。

这会显著减少长回答中的字符串分配、JSON 解析和高频拼接，也是针对历史 `exceededCpu` 的直接架构修正。客户端继续负责 SSE 解析。

本地构建、API 路由测试和真实长流均已通过。但旧线上日志中的 `cpuTime=1939ms / outcome=exceededCpu` 不能用本地结果宣告消失；必须部署后用同一复杂输入重新抓取 Workers Logs，比较 CPU 分布后才能关闭线上 P0。
