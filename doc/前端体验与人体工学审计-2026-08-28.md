# 知脉 Connect 前端体验与人体工学审计

> 日期：2026-08-28  
> 性质：只读基线，不包含产品源码改动  
> 目标：为关系核心与 Agent 重构提供真实桌面操作基线；重构后按同一视口、同一数据重新回归。

## 1. 审计环境与范围

- 浏览器：本机 Chrome，由 Playwright 驱动。
- 视口：`1366 × 768`、`1920 × 1080`，浏览器缩放 100%。
- 数据：设置页内置的 50 人、80 关系合成数据；录入页内置离线演示草稿。
- 操作路径：
  1. 录入空态 → 加载离线演示草稿 → 滚动到确认入库；
  2. 设置 → 载入 50 人/80 关系合成数据；
  3. 人物档案 → 关系网 → 单击节点聚焦 → 点击空白清除；
  4. 新建关系 → 查看关系详情 → 编辑圈层；
  5. 提醒 → “这事该拜托谁” → 离线演示问题；
  6. 日历；
  7. AI 助理 → 模型配置 → 问一问。
- 本地证据：`test-results/ux-audit/` 中保存了两种视口的截图、DOM 指标与只读操作脚本。该目录属于测试产物，不应随生产包发布。

## 2. 定量基线

| 界面 | 1366 × 768 | 1920 × 1080 | 主要含义 |
| --- | ---: | ---: | --- |
| 空白录入页总高 | 768 px | 1080 px | 空态基本能在一屏内完成 |
| 离线草稿总高 | 5493 px | 6003 px | 只有 7 个顶层条目，却需要约 5.5–7 屏复核 |
| 草稿首卡位置 | y=1308 px | 同样在首屏以下 | 用户先经过标题、引导、输入框和说明，才看到审核对象 |
| 草稿末卡位置 | y=5380 px | 接近页面底部 | 长材料的人工核验会线性变长 |
| “确认入库”位置 | y=5396 px | 接近页面底部 | 提交动作不可持续感知 |
| 人物档案页总高 | 3029 px | 2993 px | 50 人全部铺在同一长页 |
| 关系网页总高 | 4525 px | 4706 px | 图后继续铺 80 条关系记录 |
| 关系网首屏可见控件 | 39 个 | 39 个 | 其中约 33 个按钮、6 个输入或选择控件 |
| 提醒页总高 | 1989 px | 1989 px | 推荐能力位于生日、长期未联系和待办之后 |
| 到达“这事该拜托谁”的滚动量 | 约 1221 px | 约 909 px | 核心能力没有核心入口 |
| 日历页首屏可见控件 | 45 个 | 74 个 | 月历日期按钮和人物选择按钮同时造成高密度 |
| AI 助理页总高 | 818 px | 1080 px | 1366 下模型配置几乎占满首屏，聊天区仅露出底部 |

补充结论：两个视口都没有页面级横向溢出，这是当前响应式实现中值得保留的部分。

## 3. P0：重构必须解决的问题

### P0-1 录入审核不是可扩展工作流

离线演示草稿仅有 7 个顶层条目：2 个人物、1 个 Fact、1 条关系、1 个事件、1 个提醒、1 份证据。页面却延伸到 5493 px，并生成 7 个“接受此项”和 7 个“拒绝此项”。用户修改一项后还可能需要重新接受，提交按钮只在最底部出现。

真实的复杂家谱、聊天记录或批量圈层变更会把这种线性卡片流放大到不可操作。增加更多提醒、弹窗或二次确认不是解决方法。

建议改为审核工作台：

- 顶部或左侧显示人物、关系、事件、提醒、证据的数量与待确认数量；
- 高置信、无冲突项目默认折叠成紧凑行；只展开冲突、低置信和缺字段项目；
- 支持按组接受、按选择接受、接受全部安全项；
- 使用 sticky 底栏持续显示“待确认 N 项 / 拒绝所选 / 接受所选 / 确认入库”；
- AI 批量修改显示为一个分组 Diff 提案，允许展开后排除个别项，不生成几十个独立审批卡。

验收标准：

1. 1366 × 768 下，审核摘要、待确认数量和主要批量操作无需滚动即可看到。
2. 当前 7 项离线草稿若均无冲突，用户至多通过“接受全部安全项 → 确认入库”两次主要点击完成。
3. 30 项草稿中只有 3 项冲突时，界面默认突出这 3 项；其余 27 项不要求逐项点击。
4. 用户在任意草稿位置都能看到或唤回提交动作，不必滚到页面底部。
5. 修改条目后，系统只重新打开受影响条目的审批，不把整批项目全部打回。

### P0-2 关系图把“全部装下”误当成“看得清”

50 人/80 关系自动适配时，节点、姓名和边标签缩到数像素。1366 与 1920 下，巨型页面标题、页面引导、关系卡、入口说明、六个筛选器、圈层图例先占据约 500–650 px，关系图只能露出一部分。图后又完整渲染 80 条关系，页面高度超过 4500 px。

建议把关系页改成应用式工作区：

- 进入关系网后使用紧凑标题和工具栏，画布占据主要视口；
- 关系明细进入可搜索、可虚拟化的侧栏或抽屉，不再全部堆在图后；
- 实现语义缩放：远景只画结构和关键人物，不把所有文字缩成不可读的小字；选中、悬浮或放大时再显示姓名和边标签；
- 默认显示可解释骨架或局部视图，不以“一屏容纳所有细节”为目标；
- 全屏能力保留，但不应成为“只有全屏才可读”的补救。

验收标准：

1. 1366 × 768 下，进入关系网后无需页面滚动即可同时看到主工具栏和至少占视口高度 60% 的图画布。
2. 50 人/80 关系概览中，不出现低于 10 CSS px、肉眼无法辨认却仍被绘制的标签；远景可隐藏非关键标签。
3. 关系明细默认不将 80 行全部加入文档流；搜索或打开抽屉后才加载/虚拟化展示。
4. 点击节点、点击空白清除、缩放、拖动和打开人物卡不会导致页面跳动或丢失当前视图。
5. 200 人数据下仍能通过搜索、圈层或局部聚焦找到目标，不要求先看清完整总图。

### P0-3 新建关系时图和编辑器不能同时看见

1366 下，新建关系编辑器位于 y=418–668，高约 250 px；关系图从它下方开始，节点几乎完全落在折叠线下。用户必须滚到图中选择起点和终点，此时又看不到已选人物、关系名称和方向设置。

建议把新建关系改成图旁固定侧栏或覆盖在图角落的紧凑浮层。图点击和可搜索人物选择应是并行入口，而不是只能在微小总图里找节点。

验收标准：

1. 1366 × 768 下打开“新建关系”后，图、起点、终点、关系名称和确认动作能同时处于一个工作视口。
2. 常规流程不发生纵向页面滚动：打开 → 选起点 → 选终点 → 填关系 → 确认。
3. 起点和终点都支持按姓名搜索；大型图不强迫用户精确点击微小节点。
4. 关系方向默认由规范关系类型决定；手工单向/双向仅在高级设置中出现。

### P0-4 核心推荐能力被埋在提醒页底部

“这事该拜托谁”是冻结叙事中的核心能力，但当前位于提醒页最底部。1366 下需滚约 1221 px，1920 下需滚约 909 px。新用户很容易把产品理解成生日提醒工具，而不是关系行动助手。

建议提升为独立“找人/办事”工作区。若不增加侧边栏项目，可把“提醒”和“日历”合并为“日程”双标签，腾出一个核心入口。

验收标准：

1. 从全局导航一次点击即可进入推荐工作区。
2. 问题输入框和主操作在 1366 × 768 首屏可见。
3. 系统自动识别开放推荐与指定目标，不要求新用户先理解多种内部算法模式。
4. “AI 全库分析”“允许推导边参与”“离线演示问题”等高级或演示选项不占据默认主流程。

### P0-5 页面切换沿用旧页面滚动位置

各功能只是同一路由中的 `view` 状态。侧栏切换只更新 view，没有管理滚动。本轮从推荐页底部切到日历后，日历落在 y=847（1366）或 y=503（1920），直接显示“记一件事”，月份和月历标题不在视野中。

验收标准：

1. 一个功能首次进入时定位到顶部或该功能定义的主工作区。
2. 若需要保留滚动，每个功能独立保存自己的滚动位置；不能把 A 页的滚动量直接套到 B 页。
3. 浏览器前进/后退和侧栏切换行为一致且可预测。

### P0-6 关系详情不能直接修正关系本身

当前关系详情只有“关系图展示”和“引荐推荐策略”两个可编辑选择框；关系标签、方向、依据、置信度等均为只读。图后的关系列表只能切换方向、确认、查看详情或删除。用户要把“同事”改成“前同事”，只能删除重建或转去 AI 助理，直接编辑路径不完整。

验收标准：

1. 关系详情提供明确“编辑”入口，能修改规范类型、展示名称、方向/角色、限定条件、依据和有效时间。
2. 修改前后以 Diff 展示；涉及推导依赖时明确列出受影响关系。
3. AI 修改和人工修改使用同一种领域命令与审批视图，不形成两套互不一致的编辑体验。

## 4. P1：完成核心重构后应同步处理

### P1-1 AI 助理的信息架构倒置

1366 下模型配置约占 370 px，“问一问”只在页面底部露出约 150 px。页面标题也是“挑一个顺手的模型”，而不是用户当前要完成的任务。

建议：AI 助理默认显示聊天；顶部只保留当前模型徽标和切换入口。完整 provider、Base URL、API Key、看图与语音能力配置移到设置页。

验收标准：

- 1366 × 768 首屏同时看见对话历史、输入框和发送按钮；
- 模型配置不超过一个紧凑行，完整配置通过“管理模型”进入；
- 待批准提案在对话内就地显示，不把输入框推到不可见位置。

### P1-2 Agent 轨迹不是可操作的日志

当前 `ReasoningDisclosure` 实际是一个带 `title` 的普通 `div`，历史只能鼠标悬停查看；键盘和触屏无法展开，也没有工具输入/输出、耗时、token、预算和错误信息。

建议统一三个 Agent 的运行日志：

- 每次运行显示紧凑摘要：`完成 · 7 轮 · 3 个工具 · 4.2k token · 18 秒`；
- 点击打开“运行详情”右侧抽屉，包含时间线、工具 I/O、提案与审批、预算、错误；
- 日志按 `runId` 本地保存，可复制或导出 JSON；密钥、认证头和敏感字段脱敏；
- 录入、推荐和问答共用同一套日志组件与事件模型。

预算设置建议：

- 全局默认放在“设置 → Agent 执行”；
- 聊天发送区的 `···` 只配置本次运行；
- 普通用户默认看到“快速 / 标准 / 深入”三档；轮次、token、超时等数值放到高级展开；
- 达到预算时明确说明是轮次、token、总时长还是无活动超时，而不是统一显示“模型失败”。

验收标准：

1. 鼠标、键盘和触屏都可打开日志。
2. 每一次工具调用有名称、参数摘要、结果摘要、开始/结束时间和状态。
3. 用户可以设置并看到实际消耗的最大轮次和 token 上限。
4. 三个 Agent 的日志字段、视觉结构和错误分类一致。

### P1-3 圈层管理不支持真实批量整理

当前圈层弹窗宽约 448 px、高约 614 px。成员只能逐行移出，每次只能从下拉框加入一个人。图例中的每个圈层又拆为“编辑”和“只看”两个按钮。

建议引入独立 CircleMembership 管理工作台：搜索、勾选、批量加入、移出、移动；人物允许多个用户标签，主显示圈层只是一种视图设置。AI 对“把亲戚圈层中的红楼梦人物改到虚构圈层”应生成一个分组提案：创建圈层、加入 N 人、从原圈移出 N 人，用户一次批准并可展开排除个别人。

验收标准：

1. 20 人跨圈移动在 5 次以内主要操作完成，不逐人打开弹窗。
2. AI 批量圈层提案只有一个总审批区，同时支持逐项排除。
3. 圈层图例单击完成筛选，编辑进入 `···` 菜单，不为每个圈层重复绘制“只看”。
4. 用户标签、相对“我”的关系圈和算法社区在文案和视觉上明确区分。

### P1-4 关系工具栏选项过多且层级相同

默认同时出现布局、视图、关系标签、关系类别、证据模式、确认状态、边标签等控件；圈层图例又产生两倍按钮。“临时查看全部”与“全部：包含常隐”语义重复。

建议默认只保留人物搜索、视图、新建关系、全屏四类主要操作。类型、类别、证据、确认状态合并到“筛选（N）”；布局和边标签合并到“显示”。删除重复入口。

验收标准：

- 1366 下关系图主工具栏不换行；
- 默认可见的主操作不超过 7 个；
- 所有生效的隐藏筛选都以数量或筛选标签可见，避免“图上怎么少了人”的疑惑。

### P1-5 首访引导和长期界面混在一起

人物页同时出现全局 PageGuide 和“档案页”二级引导；内联建档表单、前往安全录入等入口又与侧栏录入重复。引导有利于第一次使用，但会长期压缩主工作区。

验收标准：

1. 首次引导关闭后保持关闭，只留统一的 `?` 帮助入口。
2. 同一动作只有一个主入口；“建档”使用按钮或抽屉，不长期占据整行输入表单。
3. 空态可以更教育化；已有大量数据时自动切换为紧凑工作态。

### P1-6 人物选择和日历随数据量线性铺开

1920 日历首屏出现 74 个控件，其中人物选择把大量人物直接渲染为按钮。数据从 50 人增长到 200 人后，这一模式会成为新的长页。

验收标准：

- 人物选择改为可搜索多选框，默认只显示已选人物和最近使用者；
- 200 人资料库下，事件录入区不会渲染 200 个常驻按钮；
- 月历保留日期的公历/农历可访问名称，但视觉文字根据空间分级展示。

### P1-7 视觉密度与疲劳

当前浅色主题大量使用 10–11 px 灰色文字、细灰边框和相似白色卡片。巨型标题与极小数据文字之间反差过大；关系线和关系标签在浅色背景上过淡。

验收标准：

1. 核心正文和操作标签默认不低于 12 px，重要数据不低于 13–14 px。
2. 关系线、选中状态、待审批状态满足足够的明度差，不仅依赖颜色。
3. 卡片层级通过留白、标题和分组建立，不为每一小块都增加边框。
4. 1366 × 768 连续完成录入、审核、查关系、找人流程时，不需要频繁大幅滚动和视线往返。

## 5. 应保留的交互

- 单击节点只聚焦并淡化无关节点，不再裁掉整个图。
- 点击图中空白区域可以恢复所有节点高亮。
- 双击节点打开人物卡，拖动、缩放和全屏均可用。
- 新建关系允许自由输入关系名称，而不是只能选预设标签。
- 圈层弹窗在 1366 × 768 下尺寸适中，没有超出窗口。
- AI 修改使用“尚未写入 / 批准并执行”门禁。
- 月历已经提供公历与农历的可访问名称。
- 两个桌面视口均没有页面级横向溢出。

## 6. 重构后回归清单

使用相同两种视口和同一份 50 人/80 关系数据，至少复测：

1. 7 项、30 项、100 项录入草稿的审核操作数和滚动量；
2. 新建关系时图和编辑器是否同时可见；
3. 人工直接把“同事”改为“前同事”；
4. AI 批量移动红楼梦人物圈层，排除其中一人后批准；
5. 关系图默认骨架、单击聚焦、空白清除、两跳、全屏；
6. 50/80、200 人稀疏图、40 人稠密图的可读性和响应时间；
7. “这事该拜托谁”从导航进入、开放问题和指定目标问题；
8. AI 助理修改关系提案、批准后再次查询；
9. 三个 Agent 的日志、工具 I/O、轮次与 token 预算；
10. 在长页底部切换到其他功能，确认滚动状态不会串页；
11. 仅键盘完成筛选、展开运行日志、批准提案和新建关系；
12. 200 人时日历事件的人物搜索与多选。
