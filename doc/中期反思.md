# 中期反思：确定性、智能与人的边界（v2）

> 记录日期：2026-08-28 ｜ 定位：产品与架构的阶段性自我反思。v2 新增两件事：① 把当下存在的具体问题写清楚；② 对"批准疲劳"与 full access 全局授权做出产品裁决。
> 触发问题：我们当前遇到的问题，是否来自"确定性/稳定性的过度追求"与"现实生活场景的复杂性"之间不可调和的矛盾？
> 先给结论：矛盾真实存在，但**不是不可调和，而是边界画错了地方**。我们不是把确定性用多了，而是把确定性用在了本该由智能理解的位置；同时又把本该确定的东西（亲属闭包、账本）一度交给了智能心算。

---

## 1. 问题的重新表述

用户可以有各种各样的输入，提前计划好几乎不可能。这是事实。大语言模型（LLM）把"理解自由文本"的成本降到了可以商业化的水平，于是我们想用它消化这种复杂性。

但一个关系记忆产品的核心承诺不是"理解"，是**可信**。用户把"我爸爸的爸爸""暗恋六年""上周答应帮的忙"交给系统，他需要的是：一年后打开，这些事实仍然是他确认过的事实，推导关系仍然能追溯，AI 的建议不会把他的档案改写。

于是两个力量在同一件产品里相遇：

- **智能**是概率性的、上下文相关的、不可重复的——它适合理解；
- **可信**是确定性的、可审计的、可重复的——它需要账本。

过去三天我们犯的错误，是把这两股力量放在了**同一件对象**上互相竞争：

- 用正则词表让本地代码"理解"自由文本（`circle-tags.ts` 的 `AUTO_RULES` 从备注里猜"同事"）；
- 用意图词表让本地代码"理解"用户问题（`connection-paths.ts:136` 的"找/联系/引荐"）；
- 用症状词表让本地代码"理解"现实与虚构（`assistant-request-router.ts`）；
- 反过来，又曾让模型"计算"亲属闭包（旧的 `kinship-engine` 双轨时代），拿概率产物冒充账本事实。

当确定性规则假装理解，它必然漏、必然错；当模型假装成账本，它必然漂。**冲突看起来不可调和，是因为我们在同一个维度上同时追求两个目标。** 解药是把维度拆开：不同能力，不同主体，不同信任等级。

## 2. 历史复盘：三个阶段的越界

### 阶段一：没有边界（6fd7028，8-26 14:03）

第一版是 Lovable 生成的企业版改造体，36,116 行 src。它有两大基因缺陷：

1. **数据契约太薄**：`RelationRecord` 只有 label/note/sourceId，没有依据、置信度、证据模式、语义谓词。这决定了后来所有防御都是"事后补字段"。
2. **AI 调用没有抽象**：录入是单次 `askText` 加一句"材料里没写的字段留空，绝对不要编造"。没有循环、没有工具、没有阶段。这句"绝对不要编造"把事实与推断一刀切锁死，成为亲属推导 bug 的直接起源。

这一阶段的边界问题不是"错"，是**缺失**：没有地方放智能，也没有地方放账本。

### 阶段二：越界与补丁（8-27～8-28 凌晨）

为了补能力，开始打补丁：8 轮循环、人物/事件工具、关系工具、校验回炉、批量调用。补丁带来了能力，也带来了三个病：

1. **双轨推导**：模型按提示词推一遍，本地引擎推一遍，查重靠字符串键。元春↔探春出现"姐妹"和"同父异母兄弟姐妹"两条边——两个主体在同一个事实对象上各执一词。
2. **防御复制**："原文：/推断依据："前缀约定在五个文件里各实现一遍；语义分类两套；查重键两套；校验三层。每修一个 bug 就多一层防线，防线之间开始互相矛盾。
3. **契约漂移**：提示词里广告批量工具，解析器不实现；历史截断先整体序列化再切字符串。提示词和执行器是两个世界，靠人肉同步。

这个阶段的教训不是"防御太多"，而是**防御没有长在结构上，长在了行为上**。真正的稳定性应该来自事务、模式、唯一事实源；而我们造的是词表、正则和重复校验。

### 阶段三：下沉与收敛（当前工作区）

当前重构第一次做对了方向：

- 事实断言与确定性投影分层（`relation-ontology.ts` + `kinship-projector.ts`，双轨引擎删除）；
- 三 Agent 共用工具注册表、预算账本、运行日志（`agent-tool-registry.ts`、`agent-runtime.ts`）；
- 统一批量变更计划与事务提交（`archive-mutation-plan.ts`）；
- 档案事实双通道（`agent-output-grounding.ts`：模型只选 `sourceRef + quote`，事实句由本地规范生成）；
- 急症等场景的 0 轮本地路由（`assistant-request-router.ts`）。

但最后一道门未过、且 A 组测试暴露的问题说明：**结构收敛了，边界哲学还没写完**。圈层标签仍在用正则理解语义，目标意图仍在用词表理解意图。这两处是阶段二思想的残余，藏在阶段三的新结构里。

## 3. 为什么这个矛盾看起来不可调和

### 3.1 信息不对称的两端

LLM 拥有**理解力**但没有**确定性**：同样的输入，两次输出可以不同；它甚至会被自己的输出说服。本地代码拥有**确定性**但没有**理解力**：它只能匹配模式，无法处理否定、指代、省略和歧义。

用户输入落在两者之间：自由、含混、充满指代与否定。任何单一主体都无法同时胜任：

- 只信 LLM：产品变成"看起来都对的记忆幻觉"；
- 只信规则：产品变成"必须按词表说话的表格"。

### 3.2 LLM 降低了理解成本，但没有降低验证成本

这是过去没有这类产品的真正原因，也是它现在可能存在的窗口：

- 大模型出现前，把"我大姑有一个儿子和一个女儿"变成结构化关系，需要人逐条录入，成本高到不可行；
- 大模型出现后，理解成本坍塌——几秒钟能抽出一整张关系表；
- **但验证成本没有坍塌**：用户仍然必须确认"元春是王夫人生的"是否被抽对、推导的"同父异母"是否可信。验证成为新的瓶颈。

因此这个品类的竞争壁垒不是"谁家模型理解得更准"，而是**谁能让验证成本最低**：每一条 AI 事实带依据、每一条推导可追溯、每一次修改可撤销、每一个建议可一键批准。这就是我们文档里反复出现的 basis/confidence/evidenceMode/derivedFromRelationIds——它们不是防御，是产品本体。

### 3.3 "自动"与"可信"的张力只能靠第三个角色化解

自动化的极致是无人参与，可信的极致是每一步都有人确认。两个目标直接相斥，但引入**人**之后可以同时达成：

- AI 负责**提议**（理解自由文本、判断意图、起草话术）；
- 本地负责**执行**（事务、ID、排序、路径、审计）；
- 人负责**签字**（确认草稿、批准提案、推翻判断）。

**但"签字"不等于"逐条批准"。** 签字的正确形态是收据，不是收费站：用户面对的不是 N 个弹窗，而是一张"N 条变更"的汇总单和两个按钮——"全部接受"与"全部撤销"。用户协议可以一滑到底，但平台仍然保留了同意记录与责任链条；vibe coding 敢全权限，是因为有 git、revert 与测试兜底。我们的产品必须给出等价的兜底：**事务、撤销、日志、机器可恢复备份**。有了它们，批准粒度才可以放心放宽到"一键"。

## 4. 边界原则（此后一切改动的判据）

### P1 谁生产事实，谁承担审计
任何 AI 产出的事实都必须携带可回查依据（sourceRef/quote/basis），在用户确认前保持待核验状态。没有依据的事实不允许入库，不允许进推荐，不允许被模型复述。审计责任不可放宽；可放宽的只是用户确认的粒度。

### P2 确定性只做"可证明的闭包"
本地规则只允许做逻辑上可证明的运算：由已确认断言投影出祖孙、兄弟姐妹、路径、排序、去重。它**不允许**从自由文本猜测语义——猜语义是模型的工作。

### P3 理解权归模型，执行权归本地
- 模型可以提议：这是谁、是不是目标人物、这属于什么意图、该打什么标签；
- 本地负责校验与执行：ID 是否存在、路径是否可达、排序是否锁定、写库是否事务化；
- 防注入锁的是**执行层**（rankingLocked、事务、sourceRef 白名单），不是**理解层**。

### P4 任何正则/词表规则必须可测试，且必须配负例
一条规则如果不能给出 5 个正例和 5 个否定/变体负例，它就是在假装理解，应该删除或改为 AI 提案。`AUTO_RULES`、"找/联系/引荐"词表、急症正则都没有负例语料——这正是它们咬人的原因。

### P5 写入只走一条路径
AI 的一切输出最终只能成为提案（draft/proposal），批准后经唯一事务入口提交；撤销必须能回到提交前的完整状态。不允许任何 UI 路径直接 `put*`。

### P6 用户不承担本地规则的错误
A 组"不同公司→同事"这类错，若靠"提醒用户手动编辑"解决，等于让用户给正则擦屁股。人可以纠正 AI 的误判（那是签字的应有之义），但不该纠正确定性代码的误判——确定性代码错了就该删规则，而不是增加人工步骤。

### P7 信任可调，账本不可调
批准粒度是一个用户可调旋钮：逐条确认 / 汇总确认 / 全自动写入。**无论旋钮拧到哪一档，以下不变量永远不关**：
1. 所有变更只经事务提交，可整体撤销到提交前快照；
2. 每次 AI 写入都有运行日志：谁（模型/预设）、改了什么、依据是什么、何时批准；
3. ID、schema、谓词、可达性等本地校验永远执行；
4. 禁止自动外发（发消息、邮件、对外系统操作）永远生效；
5. 急症 0 轮路由永远先于模型。
Full access 放宽的是"打断次数"，不是这五条。

## 5. 当下存在的具体问题（必须作为哲学验证的靶子）

### 5.1 圈层标签：本地规则在做语义理解（已实测复现）

### 5.2 目标意图：词表替 AI 判断意图（已实测复现）
- 位置：`src/lib/connection-paths.ts:126-151`（意图词表 `找|联系|接触|拜访|请教|引荐|介绍|通过谁|办事|约到|牵线`）。
- 复现 B1："我想**给贾母送一份寿礼**，应该怎么安排？"→ 不进目标模式，候选变成摄影/设计关键词匹配，完全不提贾母。
- 复现 B2：单字姓名"婷"因别名过滤 `length>=2` 永远不能成为目标。
- 性质：用户不会按词表说话。违反 P3（理解权被本地抢占）。

### 5.3 急症路由：正则判断现实与虚构
- 位置：`src/lib/assistant-request-router.ts:13-55`。
- 漏报样例："家里老人**心绞痛**发作，现在怎么办？"、"胸口像**压**了块大石头"。
- 误报样例："帮我写一句广告**文案**，表现胸痛伴冷汗的感觉"（"文案"不在非真实场景白名单）。
- 性质：不是当前比赛重点，但它是 P4 的最典型反例——规则在无负例语料的情况下运行于安全边界。

### 5.4 数据卫生（赛后处理）
- `archive-agent-tools.ts:48`：手机号脱敏正则被 `+86` 前缀绕过（`+86 138...` 原样进提示词）；
- `identity-match.ts:19-24`：+86/全角数字不归一 → 同人重复建档；
- `personal.ts`：2 月 29 日提醒滚到次年 3 月 1 日。
- 性质：不影响主线演示，但都属于"确定性代码未配负例"的旧债。

### 5.5 批准疲劳真实存在，且当前没有信任旋钮
- 现实：所有 AI 写入都要人工批准；没有"汇总确认"的轻量形态，更没有任何"全自动"形态。
- 后果：用户要么被打断到烦，要么不认真看——两种都让"审计"失去意义。
- 用户类比成立：协议被一滑到底，是因为没有更好的形态，不是用户不需要知情。产品要做的是**收据式确认**（见 6-E）。

## 6. 具体决策的裁决

### A 圈层识别：本地规则退出语义判断
- 关系图分组直接使用用户确认过的 `profile.circle`（或确定性映射出的 tag），删除/停用 `AUTO_RULES` 对自由文本的猜测；
- "AI 智能纠错整理"保留，但形态必须是**提案流**：AI 提议改圈层 → 显示依据与前后差异 → 用户批准 → 事务提交。它只能降成本，不能加风险。

### B 目标意图：给 AI 理解权，保留本地执行权
- 删除意图词表。目标模式改为：本地先把问题中命中的档案名候选交给模型，模型提议"目标是谁/是否目标模式"，本地校验其 ID 真实存在；
- 路径计算、可达性、排序、分数仍然 `rankingLocked`，AI 只解释与起草；
- 单字姓名、同名消歧照常工作（消歧仍由人签字）。

### C 急症路由：保持最小确定性，不扩展
- 只保留"持续胸痛伴冷汗、无呼吸/呼吸停止、大出血"三个绝不等待的硬短语；
- 其余全部交给模型，系统提示顶部加一行安全建议；不再追求用正则区分小说与真实；
- 判断原则：**宁可在创作场景误提醒一次 120，不可在真实急症等一轮模型。**

### D 数据卫生：赛后处理
- +86 手机号脱敏、身份归一、闰日提醒等按缺陷清单排期，不在比赛前抢占重构时间。

### E 授权模式：加入 full access 全局旋钮（本次反思新增裁决）
设置中加入三级授权，默认**标准**：

| 档位 | 录入/整理 | 问一问 / 找谁帮忙 |
|---|---|---|
| 谨慎 | 逐条确认草稿项 | 每次 update 生成提案，逐条批准 |
| **标准（默认）** | 一张汇总单 + 一个"确认入库"按钮 | 会话内所有更改排队，结束时给一张汇总单："N 条更改 · 全部接受 / 全部撤销" |
| 全速（full access） | 点一次最终"录入"按钮，整批事务提交（现状草稿页基本已接近此形态） | AI 可调用全部本机工具，更改直接进入同一事务队列；回答底部常驻"本次已改 N 条 · 撤销"；删除人物/关系仍保留一次确认 |

Full access 打开后仍然不可关闭的东西（对应 P7 五条）：
1. 事务与撤销：一次提交 = 一个可整体撤销的 checkpoint；
2. 日志：每次运行留下"哪个预设、哪个问题、改了哪些记录、依据"的可脱敏记录；
3. 校验：ID/schema/谓词/可达性本地校验不因授权而跳过；
4. 禁止外发：任何模式下不自动发消息或操作外部系统；
5. 急症路由：任何模式下 0 轮先行。

上线前提：`archive-mutation-plan` 事务与撤销路径通过测试后，full access 才允许开放；若 8/31 前来不及验证，该选项先隐藏，比赛用"标准"档。

2. 删除阶段二遗留：`relation-semantics.ts`、`relation-graph.ts` 若已无消费者则移除，`AUTO_RULES` 退役；
3. 上线 E 三级授权：full access 在事务/撤销测试全绿后开放；
4. 建立"规则负例语料"制度：每新增一个正则/词表，必须同时新增正反例测试；
5. 用真实使用数据度量两个指标：AI 提议的**采纳率**（验证成本是否在降）与**修正率**（理解质量是否在升）。此后所有"要不要加一条规则、要不要加一次批准"的争论，都以这两个数字裁决，而不是以感觉裁决。

---

## 8. 一句话总结

> 我们不是在"给 AI 加限制"与"放开 AI"之间摇摆，而是在学习一件更基本的事：**让概率性的智能负责理解，让确定性的账本负责事实，让人负责签字——而签字可以是一键收据，不必是收费站。** 每一次把这三个角色混在一个主体里，或者把批准粒度误当成账本本身，都会以 bug 或疲劳的形式把边界还给我们。
