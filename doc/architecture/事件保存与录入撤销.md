# 事件保存与录入撤销

## 事件保存

日历打开事件时固定原始记录；列表刷新不推进编辑基线。`compareAndSwapLifeEvent` 在同一个 IndexedDB `readwrite` 事务内检查完整记录修订、检查参与人物、写入事件和写入决策标记。时间戳不是修订号。创建使用 `expectedRevision: null`，仅允许目标 ID 尚不存在；编辑要求内容修订相等，删除后的记录不会被意外复活。

一次保存意图保留稳定 ID、写入内容与决策 ID。重复点击由同步守卫拦住，提交确认丢失后的同一意图重放是空操作。冲突必须重新打开或取消编辑才能更新基线。标题和详情分别检查 500 / 4,000 字上限；未改变的历史文本原样保留，不在保存时截断。

明确日期、完整日期范围、月范围和年范围共用公历校验；明确非法输入不会回退为年份、首日或交给模型猜测。无法识别的自然语言仍可使用原有 AI 辅助。年/月精度往事不进入今天急办；现有 range 的进行中语义保持不变。

## 录入收据

批准后的录入写入沿用 `applyArchiveMutationBatch` / `applyArchiveMutationBatchOnce`。需要撤销时传入 `undoReceiptId`。同一个事务记录实际写入前后发生变化的行（包括规范化结果和关系清理产生的变化），并在 `appMeta` 保存 `archiveUndoReceipt:<id>` 的版本 1 收据。不会在提交后重新读当前库来推测本次写入。派生关系不作为事实恢复。

收据记录 `version`、`status`、`changes` 与撤销冲突；每项变更有 store、稳定 ID、before 和 after。用户资料仍只保存在本机 IndexedDB，不进入远端日志。会话状态只需保存稳定收据 ID，刷新或重启后使用同一份原子收据；中断的批准重放不重新采集快照。

## 原子撤销

`undoArchiveMutation` 在覆盖相关存储的单一事务中完成以下步骤：

1. 当前完整内容必须仍等于该收据的 after；后来修改或删除的行保留现状。
2. 对剩余变更做依赖闭包检查。仍被保留事件、提醒、关系、证据、集合成员、任务等引用的人物或来源不删除；恢复旧行也不能引入对独立删除对象的悬空引用。
3. 一次提交全部可撤销行，重建亲属投影并标记收据已撤销。事务中止时，不留下半撤销数据；再次执行已撤销收据不会重新覆盖后来修改。

不能仅检查事件后继续级联删除其人物。冲突提示区分缺失收据与因修改/删除/依赖跳过的记录，不把部分撤销描述成全部成功。

## 兼容与恢复边界

旧 `IntakeUndoBatch` 仍可读取，旧 `committedPeople/committedEvents` 仅作为兼容字段，不能授权回滚。找不到事务收据时不写入任何记录，提示逐条检查，不退回无条件覆盖。没有改变数据库版本或 archive@2 的事实归档格式。

完整备份仍不包含运行/撤销历史。完整替换档案时，旧撤销收据权限一并失效，避免恢复后再应用另一份档案的历史撤销；恢复后的事实仍可正常编辑。事务收据保留的是完成撤销所需的本机历史值，不应作为可分享的普通诊断数据导出。
